# Relay 503 与慢启动：证据和修复边界

2026-10-31，Android 16 手机与 Via 在联通移动数据下出现入口超时、加载插件长时间不完成。调查记录包含以下两种现象，不能混为一种故障。

## 已捕获的服务端响应

```http
HTTP/1.1 503 Service Unavailable
Content-Type: text/plain; charset=utf-8
Content-Length: 25
Cache-Control: no-store
Server: cloudflare

relay storage unavailable
```

同一静态资源曾在短时间内交替返回完整的 HTTP 200 和上述 503。与本地服务正常响应的对照支持故障位于托管 Relay 链路。该自定义正文与通用 CDN 错误页不同，但服务运行在 Cloudflare 上，不能将其简单表述为“与 Cloudflare 完全无关”。

这个响应说明托管服务报告了存储不可用；尚无服务端内部日志证明具体是绑定、存储后端、配额还是其他故障。单凭响应文字不能进一步确认内部根因。App 本地修改无法修复托管服务的存储故障。

## 另一个问题：首屏资源负载

当时三份插件 bundle 的 identity 正文为 46,345、11,458,664、9,179,572 字节，gzip 正文为 14,931、4,505,334、4,209,163 字节。gzip 合计约 8.73 MB（8.33 MiB）。链路吞吐明显波动时，首次完整下载可能超过 90 秒。

两个插件内嵌了较大图片资源。应由插件/内核上游把图片拆分为可独立缓存、按需获取的资源，保留原功能。不能用禁用账号页、壁纸或主题冒充兼容性修复。本轮不修改已安装内核归档、不禁用插件、不重写资源中的凭据。

## App 本轮改动

- 启动等待超过 90 秒只显示等待说明，不再设置主文档失败。真实主文档 HTTP/网络错误仍由 WebView 回调报告；认证失败仍需要重新授权。
- 待下载资源尚未完成时，启动页的刷新保留当前请求和进度；不清零重试次数、不发起整页重下。超时提示中的“重新下载”明确说明将中断当前下载，用户确认后才重载；确认期间页面已就绪则不再重载。实际页面失败或下载已结束后仍可手动重试。
- 自动恢复仍遵守有限次数、间隔、草稿/任务/文件和资源保护，不重放业务写入。
- 可见界面探测只检查编辑区是否可见，保留早期配对确认和失效识别；不再每半秒读取整个页面的 `innerText`。

## 验证方法

```powershell
node tools/test-page-ready.mjs
node tools/test-browser-health.mjs
node tools/slow-startup-fixture.mjs 105000
```

慢启动夹具只监听电脑回环端口 18765。使用独立的 debug 应用及 USB 开发配置，通过 ADB reverse 连接；它不访问真实 DSH、不含账号、不发送模型任务。验收时观察：下载跨过 90 秒仍保持同一次文档和资源请求；点击启动页刷新不取消下载；脚本完成后可见编辑区使加载层消失。夹具成功不等于联通公网已通过。

真实入口还必须分别验收：多次冷启动、资源完整性、实时连接、无副作用的只读业务、前后台恢复。Android 17 原报告设备尚未接入，本轮不能对其作通过结论。

## 可交给 Relay 服务维护者的排查要点

1. 对照 503 时间和请求 ID，定位产生 `relay storage unavailable` 的处理分支、具体存储操作和异常类型；不能只返回统一错误而不保留内部原因。
2. 检查各部署版本、边缘节点的存储绑定、配额、读写失败与重试记录，确认是否存在版本或节点差异。
3. 将存储不可用与桥接离线、转发超时、上游应用 503 分开记录；核对失败请求是否已经进入电脑侧桥接。
4. 检查大静态响应与实时请求并发时的组帧、背压、取消传播和连接恢复；报告完整响应的字节数及耗时，而非仅看握手。
5. 修复后在同一入口重复验证完整资源和只读业务，明确观测时段与复发次数。

公开反馈应使用脱敏的请求路径、时间、状态与错误正文。不要附带私有入口域名、配对参数、Cookie、授权头、完整 HAR 或用户对话内容。
