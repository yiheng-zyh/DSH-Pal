# alpha.6 连接可靠性修复与验收边界

## 问题证据

一份 alpha.5 / Android17 日志显示配对已被接受，随后多个静态资源返回503，未出现实际工作区，原生HEAD连续4秒超时。主文档HTTP503还先于onPageStarted回调到达，后者曾清空错误，造成启动页掩盖真实故障。

Android16真机公网复核发现：页面内HEAD约5.45秒返回401（入口有响应），原生4秒探测却报超时；页面可打开时，独立业务错误还会触发原生整页自动刷新。以上均不能用USB测试代替。

## 修复

- 正常资源请求交由Chromium处理及缓存，统一TLS、Cookie、Service Worker和浏览器请求上下文。同步OkHttp代取仅保留显式USB资源实验。原实现缓存未命中时可能先等待最多120秒，失败后才再让浏览器请求。
- 扫入新配对链接时，在准备传输层后直接由浏览器验证，不让另一套原生预探测否决扫码；VPN准备失败仍回到原通道。普通已保存连接切换仍保留原有验证与回退。
- 页面已发出的主文档错误不再被后到的开始加载回调清除，真正可见的工作区恢复后才解除加载状态。
- 前台健康探测采用同源浏览器HEAD，12秒网络超时、14秒原生兜底；不请求配对链接，不读响应正文和Cookie。浏览器未就绪不计作网络失败样本。
- 只提示页面自行恢复，不强制关闭CONNECTING/OPEN通道。实时通道仍打开时，业务/可选插件故障不会触发整页刷新。
- 断线且无任务、草稿、上传、未完成写入或资源加载时才允许有限刷新；连续最多两次。主页面明确超时、429或5xx时可在浏览器上下文不可用的情况下有限恢复；认证/404/脚本异常不会因此盲重试。
- 旧服务缺失changes.summary的404/405/501记为能力受限；核心接口404和其他业务错误继续报告，不掩盖真实失败。

## 必须分别验证

冷启动、扫码首次进入、前后台恢复、无网络后恢复、正常会话不被刷新、失败按钮可操作、已保存配对保留、草稿/任务/文件不受影响。成功标准包括实际工作区、实时通道和只读业务响应，不能使用bridge存在、HTTP200或进度100%替代。

已知公网链路仍可真实返回503或较长延迟。代码修复不保证中转服务可用；Android17原报告设备尚未接入USB，不能宣称该设备已验收。国内IPv4备用接入已单独部署并测试，但 cpolar 手机稳定性未通过，详情见 [cpolar 传输说明](cpolar-transport.md)。未替换原主通道，也未推送GitHub。

2026-10-31 补充修复：顶部状态条以真实的可见界面就绪状态决定是否显示加载百分比和进度条。流式插件使 Chromium 进度停留在 10% 时，已经可用的工作区不再继续显示“加载页面 10%”；业务错误、慢请求与通道状态仍分别显示。

后续专项复核捕获 Relay 返回 `relay storage unavailable`，另有大插件资源传输停滞。App 已将 90 秒等待提醒与真实主文档错误分开，下载进行中保留请求，显式确认后才重新下载；界面就绪探测不再扫描整页文本。服务端故障与 App 缓解措施的边界、复测方式见 [Relay 503 调查](relay-503-investigation.md)。这些改动不代表托管 Relay 的存储问题已修复。
