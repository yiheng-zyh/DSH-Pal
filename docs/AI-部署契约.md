# AI 部署契约

> **这份文档是写给「接手部署的 AI」看的，不是给人看的。**
> 场景：用户把仓库链接丢给你，说「帮我把手机端配好」。你读完这一份就该知道：**要配哪些项、配到什么程度算配齐、哪些步骤必须停下来找用户**。
>
> 如果你只读了 `README.md` 就认为配完了 —— 大概率漏了通道。这份文档存在的唯一目的就是防这个。

> 人看的版本：[用户核对清单](用户核对清单.md) ｜ 连接细节：[connections.md](connections.md) ｜ App 功能开关：[features-setup.md](features-setup.md)

## 零、先认清你的职责边界（最重要，先读这段）

你**不是**「替用户把一切都搞定」的角色。项目里有**两条硬边界**，你无论如何都跨不过去：

1. **第三方账号注册与实名认证**（如 Sakura Frp 的访问密钥）—— 需要用户本人的身份与手机验证
2. **用户手机上的操作**（安装 APK、授予系统权限、扫码配对、看屏幕确认结果）—— 设备不在你手上

所以，**你的成功标准不是「全部配好」，而是这三件事**：

| # | 你必须做到 | 判断标准 |
|---|---|---|
| 1 | **把所有你能做的做完** | 部署清单里标 `AI` 的项，全部执行并验证，不遗漏 |
| 2 | **把所有你做不到的说清楚** | 每一项都明确告诉用户：需要他做什么、为什么你做不了、做完怎么告诉你 |
| 3 | **让用户清楚知道当前到哪一步了** | 交付时给出：完成了什么、还差什么、差的那步归谁 |

> **换句话说：漏掉一项「你能做的」是失职；没交代清楚一项「你做不到的」同样是失职。**
>
> 用户不需要你假装全能，他需要你**把该做的做完、把剩下的讲明白**。做不到却说"配好了"比不做更糟 —— 用户会带着一个残缺环境去用，出问题时根本不知道是哪一层。

### 三条禁止

- ❌ **不许假装执行了需要用户本人操作的步骤**（比如声称"已注册 Sakura"）
- ❌ **不许因为某项做不到就跳过整个流程**（比如因为要注册就干脆不配国内通道，也不告诉用户还有这条路）
- ❌ **不许把"配置写好了"当成"验证通过了"**（进程在跑 ≠ 手机能用，见第四节）

### 交接时你必须能回答这三个问题

如果你的回答含糊，说明你还没做完：

1. **「电脑端你配了哪些？分别验证到第几层？」** —— 要能列出通道 + 对应的验收层级
2. **「还差哪些？每项卡在谁身上？」** —— 要能区分「你还没做」和「必须用户做」
3. **「用户下一步具体做什么？」** —— 要给出可执行的动作，不是"你去配一下"

## 一、什么算「配齐」

**「手机能打开网页」不等于配齐。** 下面六项全部满足才算：

- [ ] **插件已装且已固化**：`package.json` 里 `@linxin666/dsh-remote-web-ui` 的值以 `file:` 开头（见第二节第 0 项），不是纯版本号
- [ ] **电脑端**：DSH 在跑，远程访问插件已启用，DSH webserver 保持 `127.0.0.1` + 端口 `0`（不许改）
- [ ] **至少一条公网通道可达**，且**走完了本文件第四节的分层验证**（不是只看进程在跑）
- [ ] **手机已配对**，扫码成功，设备出现在插件面板的设备表里
- [ ] **实时通道已建立**：日志有 `ws OPEN`，服务端 `onlineCount >= 1`
- [ ] **业务可用**：至少一项无副作用响应成功（打开工作区看到已有会话）

**未经验证的通道必须写"未验证"，不能因为"配置看起来对了"就报完成。**

> 注意：第 4~6 项**必须用户参与**（他得拿手机扫码、看屏幕）。你做到第 1~3 项，把 4~6 项的操作步骤清楚交给用户，**就算尽到职责**了。

> **第 1 项的意义**：App 依赖的这个插件上游已弃用、随时可能从 npm 消失。
> 不固化的话，用户今天能装、明天重装就装不上。**这是唯一一项「现在不做、将来无法补救」的配置。**

## 二、部署项清单（按优先级，逐项执行，全部幂等）

### 第 0 项：装远程访问插件（**最容易漏，也最容易装错**）

这一步在「一、什么算配齐」的清单里只写了「插件已启用」，但**没有说怎么装**。
本节补上，**因为装错方式会让用户几周后突然连不上**。

#### 为什么这一步特殊

App 依赖的 `@linxin666/dsh-remote-web-ui` **上游已弃用**。作者原话：

> *"Browser-based remote control has been replaced by the native phone app, and this
> package no longer provides remote access capabilities."*

**翻译**：作者说「浏览器远程控制已被替代，本包不再提供远程访问能力」——
而**那正是本 App 依赖的部分**。

所以：

| 风险 | 后果 |
|---|---|
| 作者从 npm 下架 0.4.14 | 用户以后重装时装不上，App 变砖 |
| 作者发新版删掉浏览器面 | 用户装 `@latest` 就白屏 |
| 用户为了「更新到最新」而升级 | 同上 |

**这三条都会在「装完之后」才爆，所以现在就必须防住。**

#### 正确做法：两条命令，先固化再装

**不要**直接 `dsh plugin add`。**先固化**，再装。

```powershell
# ① 在仓库根目录执行（不需要联网，用仓库自带副本）
node tools/vendor-plugin.mjs --profile desktop

# web profile 用户换成：
# node tools/vendor-plugin.mjs --profile web

# ② 按它打印的提示，进 profile 目录装依赖
cd $env:USERPROFILE\.dsh\profiles\desktop
pnpm install
```

**它做了什么**：

1. 把仓库自带的 `third_party/dsh-remote-web-ui`（0.4.14，已含 IPv6 补丁）复制到
   `~/.dsh/vendor/dsh-remote-web-ui`
2. 改 profile 的 `package.json`，把依赖从版本号改成 `file:` 路径（**改前自动备份**）
3. 告诉你下一步跑什么

**验证固化成功**（必做）：

```powershell
Select-String "$env:USERPROFILE\.dsh\profiles\desktop\package.json" -Pattern 'dsh-remote-web-ui'
```

**期望输出**：值以 `file:` 开头

```
"@linxin666/dsh-remote-web-ui": "file:C:/Users/<用户>/.dsh/vendor/dsh-remote-web-ui"
```

**如果还是 `0.4.14` 这种纯版本号 → 没固化成功，重跑第 ① 步。**

#### 什么时候可以用 `dsh plugin add`（退化路径）

只有在**用户明确拒绝固化**、或 `vendor-plugin.mjs` 跑不通时才用：

```powershell
dsh plugin --profile desktop add @linxin666/dsh-remote-web-ui@0.4.14
```

**两条硬要求**：

1. **必须固定 `@0.4.14`**，写 `@latest` 或省略版本号都会装到未来版本 → 白屏
2. **必须在交付报告里标注「未固化，上游下架后需重装」**

#### 装完后的验收（三层，都要做）

```powershell
# ① 依赖是否指向本地
Select-String "<profile>\package.json" -Pattern 'dsh-remote-web-ui'
#    期望：值以 file: 开头

# ② 插件是否被 DSH 加载
node tools/deploy-status.mjs
#    期望：插件检查项通过，且不报「Expected exactly one remote-web-ui plugin」

# ③ 端点是否可达（端口每次重启会变，从 DSH 日志找）
curl http://127.0.0.1:<端口>/api/pair/status
#    期望：HTTP 200
```

**三层都过才算装好。** 只看 `pnpm install` 成功不算。

#### 别做的事

| ❌ 不要 | 为什么 |
|---|---|
| 用 `@latest` 或不写版本 | 装到删了浏览器面的新版，手机白屏 |
| 为了「升级到最新」而改版本 | 上游明确说不保留该能力 |
| 装完不验证就报完成 | 用户几周后才发现连不上 |
| 手动 `pnpm add` 而不改 profile | 绕过 DSH 的 profile 管理，容易不一致 |

### ⚠️ 先想清楚用户怎么用它（这决定配哪个通道）

**这个 App 解决的问题是：人不在电脑前，还想接着用 DSH。** 所以先问自己——用户会在哪些地方用它？

| 场景 | 频率 | 手机在什么网络 | 能用的通道 |
|---|---|---|---|
| **A. 在家，但不在电脑前**（床上、沙发、卫生间、厨房） | **最高频** | 与电脑同一 Wi-Fi | 局域网最快；**公网通道也能用**（绕远一点） |
| **B. 出门在外**（通勤、地铁、咖啡厅、商场） | 高频 | 移动数据 / 别家 Wi-Fi | **只能公网**，局域网完全用不了 |
| **C. 公司 / 学校** | 高频（工作日） | 受限网络，可能屏蔽端口 | **只能公网**，且要能穿透受限网络 |
| **D. 出差 / 旅行** | 中频 | 完全陌生网络 | **只能公网** |

**由此得出一个硬结论：**

```
公网通道覆盖  A（降级可用）+ B + C + D  =  100% 场景   ← 第一阶段
局域网直连只覆盖  A                       =  1 类场景   ← 第二阶段
```

### 核心原则：**配置要完整，顺序有先后**

> **电脑端该配的都要配上。** App 里每个功能都对应电脑端的一条能力，
> 少配一条，用户在 App 里打开那个功能时就是坏的。
> **用户不用的功能，是他在 App 里关掉，不是我们不配。**

所以这不是"选哪个通道"的问题，是**两件事都要做、但有先后**：

| | 定位 | 做不做 |
|---|---|---|
| **第一阶段：公网** | 决定"能不能用"（出门也能用） | ✅ **必做**——除非用户明确拒绝远程 |
| **第二阶段：局域网** | 决定"在家快不快、省不省流量" | ✅ **必做**——除非用户明确说不要 |

**顺序不能反**，因为：

- ❌ **先配局域网**：它最快、最省事、最容易"看到成功" → 用户以为完事 → 出门发现用不了 → 判定"这 App 是坏的"
- ✅ **先啃公网**：要注册、要等证书、可能要调路由器，慢但那是**核心能力** → 真机移动数据验证通过 → 再回头补局域网

**「第一阶段彻底解决」的判据**：拿手机、关掉 Wi-Fi、只用移动数据，能进工作区并收到回复。

### 两阶段执行（顺序不许颠倒，但两阶段都要做完）

```
═══════ 第一阶段：公网（决定能不能用）═══════
P0  国内 IPv4 中转（Sakura Frp）    ← 先做这个，国内实测最可靠
      ↓ 不通才往下
P1  IPv6 直连                       ← 有公网 IPv6 时链路最短
      ↓ 还不通
P2  国外中转（Relay / Cloudflare）  ← 备选，Relay 有已知 503 故障

  ★ 阶段闸门：手机关 Wi-Fi 只用移动数据 → 能进工作区 → 才进第二阶段

═══════ 第二阶段：局域网（决定在家体验）═══════
P3  局域网直连（Wi-Fi）             ← 公网验完就配，让在家更快、少耗隧道额度
P4  USB 数据线                      ← 开发调试用
```

**第二阶段的 P3 不是"可选项"，是配置的组成部分。** 只是必须等第一阶段验证通过后再做。

### 什么情况可以不配（仅限用户明确拒绝）

| 情况 | 处理 |
|---|---|
| 情况：不需要远程、只在家用 | 可不配 P0，但**必须明确告知**：现在配置出门用不了，以后要远程随时回来加 |
| 情况：不用局域网、在家也用公网 | 可不配 P3，但要告知：在家会多绕一跳、消耗隧道额度 |
| **用户什么都没说** | **默认全配**。没说不等于不要 |

> **判断标准：用户没明确拒绝 = 要配。**
> 电脑端配全了，用户想用哪个功能都能用；配缺了，他在 App 里点开是坏的，
> 而且他不知道是"没配"还是"App 有 bug"。
**为什么必须分阶段**：局域网和公网解决的是两个不同问题。局域网解决"在家更方便"，
公网解决"能不能用"。混着配、或者先配容易的，结果是**用户以为自己配好了，
实际核心需求没解决**——这是最伤人的交付失败。

### 场景相关的实际约束（配的时候要考虑进去）

| 约束 | 为什么重要 | 怎么做 |
|---|---|---|
| **网络会切换** | 用户从家 Wi-Fi 走出门切移动数据，通道要能跟着切 | 国内通道用同一地址，切换网络后**不需要重新扫码**（Cookie 保留）。这是选它的理由之一 |
| **移动数据有成本** | 插件首屏资源 gzip 合计约 **8.73 MB**（[relay-503 调查](relay-503-investigation.md) 实测）。免费 Sakura 只有 5 GiB/月 | 首次加载后走本地缓存（96 MiB 上限，见 [static-resource-cache.md](static-resource-cache.md)），日常文字对话流量很小；局域网配好后在家可进一步省额度 |
| **用户不会一直盯着** | 切后台、锁屏后回来发现断了会很难受 | 后台保活默认开；告知用户关掉电池优化（Rom 层，App 无法自动申请） |
| **弱网是常态** | 地铁、电梯、公共 Wi-Fi | 验收时不能只在好的网络下试；至少告诉用户"弱网下会慢，不是坏了" |
| **一条通道会挂** | 隧道维护、免费额度用完、地址变化 | 第一阶段尽量留一条备选（P0 + P1，或 P0 + P2），并告诉用户怎么切 |

### 动手前先确认三件事

这三样**文档不教你装**（本仓库是手机 App + 电脑端转发工具，不含 DSH 本体）：

| 前置 | 怎么确认 | 没有怎么办 |
|---|---|---|
| **DSH 已安装并登录** | 能打开 DSH 桌面端或 `dsh web`，能看到工作区 | 去 <https://github.com/deepseek-ai> 找 DSH 官方发布，装上并登录账号。**这一步必须用户自己完成** |
| **Node.js 22 或更新** | `node --version` 显示 v22+ | 去 <https://nodejs.org/> 装 LTS。国内通道工具与自检脚本都依赖它 |
| **知道用户的 DSH profile** | 平时开桌面端 → `desktop`；跑 `dsh web` → `web` | 问用户「你平时怎么打开 DSH 的」 |

> **如果用户连 DSH 都还没装**：说明他理解的"配好"是另一件事。**先停下来问清楚**，不要硬着头皮往下配 —— 没有 DSH，后面的通道一个都用不上。

### 公网是必须项，不是可选项

**DSH Pal 的产品定位就是：人不在电脑前也能用。** 所以**公网通道必配**，配置它不需要征询用户。

**但局域网也要配。** 它决定"在家时快不快、省不省流量"。用户不用的功能是他在 App 里关掉，
不是我们不配。**电脑端配全，App 里按需开关——这才是正确的分工。**

**唯一例外：用户明确拒绝。** 没说过的都按"要配"处理。

| 阶段 | # | 项目 | 谁做 | 前置 | 验证方式 | 用户介入 |
|---|---|---|---|---|---|---|
| — | 1 | 确认 DSH 实例与 profile | AI | DSH 已运行 | 确认 `desktop` 还是 `web`，拿到回环端口 | 无 |
| — | 2 | 远程访问插件安装/启用 | AI | 1 | 插件面板出现"远程访问"入口 | 无 |
| **一** | 3 | **国内 IPv4 中转（Sakura Frp）** | **半自动** | 2 + Sakura 账号 | `tools/remote-access` 跑通 + **手机关 WiFi 用移动数据**进工作区 | **注册 + 实名 + 给密钥** |
| 一 | 4 | IPv6 直连（P0 不通时） | AI | 2 + 电脑有公网 IPv6 出口 | `configure-direct.mjs --ipv6 --status` + 手机移动数据实测 | 路由器放行入站 |
| 一 | 5 | 国外中转（P0/P1 都不通时） | AI | 2 | `status.publicUrl` 非空 / 插件报告 tunnel 地址 | 无 |

| **二** | 6 | **局域网直连（Wi-Fi）** | AI | 闸门已过 | `GET /api/pair/status` → 200 | **UAC 提权**（放行防火墙时） |

### 第 8 项「手机装 APK」具体怎么做（别只说"你自己装"）

**APK 从哪来**：GitHub Releases 页 <https://github.com/yiheng-zyh/DSH-Pal/releases>

1. 用手机浏览器打开上面这个链接（**别用微信内置浏览器**，下不动大文件）
2. 找**最新**的那个 Release（带 `Pre-release` 标记是正常的，当前是开发预览版）
3. 展开 `Assets`，下载 `.apk` 文件
4. 下载完点开安装。系统会提示"未知来源应用" → 允许本次安装
5. 装完在桌面看到 **DSH Pal** 就成功了

**下载慢怎么办**：GitHub 在国内经常很慢。有两个办法：

1. **让 AI 用镜像下载好再传到手机**（推荐）。国内加速镜像可用 `gh-proxy.com` 前缀，例如把
   `https://github.com/.../DSH-Pal-xxx.apk` 换成 `https://gh-proxy.com/https://github.com/.../DSH-Pal-xxx.apk`
   下载后用微信/QQ 传给自己。
2. **手机插着数据线直接装**（不卸载、保留数据）：

```powershell
adb -s <手机序列号> install -r <下载好的 apk 路径>
```

**装的时候可能遇到的问题**：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 手机上已有**别的签名**的 DSH Pal | **不要卸载**（会丢配对和授权）。让 AI 用正确签名重新构建后 `install -r` |
| 提示"应用未安装" | 下载不完整或包损坏 | 重新下载，或用镜像工具下载后校验大小 |
| 找不到下载的 apk | 浏览器存到了下载目录 | 手机文件管理 → 下载 里找 |

### 第 9 项「手机权限与功能开关」和扫码配对的具体位置

**扫码配对在 App 里的路径**（装完 App 后）：

### 默认策略（必须照做，一条不落）

```
第一阶段（公网）—— 做完并真机验证
  1. 配 P0 国内 IPv4 中转。不需要问用户，直接配。
  2. P0 不通、或电脑有公网 IPv6 → 加配 P1 IPv6 直连。
  3. P0/P1 都不通 → 才退回 P2 国外中转（Relay 有 503 故障，别当主路径）。
  4. ★ 闸门：手机关掉 Wi-Fi，只用移动数据，能进工作区并收到回复。

第二阶段（局域网）—— 闸门过了就配
  5. 配 P3 局域网直连（必做，非可选）：让在家更快、不消耗隧道 5 GiB/月额度。
  6. 配 P4 USB 调试入口（开发场景需要时）。
```

**顺序纪律（核心，别搞反）：**

- ❌ **不许先配局域网再配公网。** 局域网最快、最省事、最容易"看到成功"，
  先弄它会让人以为完事，出门才发现用不了。
- ✅ **公网必须先啃下来**，哪怕要等用户注册实名、等证书签发、调路由器。
- ✅ **公网通了之后，局域网照配**，不是"公网通了就够了"。
- ⚠️ 公网卡住时**如实告诉用户卡在哪**，不要用"局域网已配好"掩盖没完成的部分。

**为什么两条都要配**：电脑端少配一条，用户在 App 里打开对应功能时就是坏的，
而且他分不清是"没配"还是"App 有 bug"。**电脑端负责完整，App 负责按需开启。**

### 什么时候可以不配（必须用户明确拒绝）

| 情况 | 可以不配 | 必须告知 |
|---|---|---|
| 「我不需要远程，只在家用」 | 第一阶段公网 | 现在配置出门用不了，以后要远程随时回来加 |
| 「局域网不用，在家也用公网」 | 第二阶段局域网 | 在家会多绕一跳、消耗隧道免费额度 |
| **什么都没说** | **都不行，全部要配** | — |

> **判断标准：用户没明确拒绝 = 要配。**
> 不要把"用户没提"当成"用户不需要"——他不知道有这东西，怎么会提？

> 依据：Relay 有已知服务端 503 故障（[relay-503-investigation.md](relay-503-investigation.md)）；国内 IPv4 中转已在国内移动数据下实测可进工作区（[tools/remote-access/README.md](../tools/remote-access/README.md)）。

### 两个可选插件（默认**不装**，但必须主动告知用户它存在）

> ### ⚠️ 先分清 DSH 的两种插件安装机制（**混用会装不上**）
>
> 本项目提供的插件分两类，安装方式**完全不同**。这是 2026-11-05 实测确认的：
>
> | 类型 | 特征 | 怎么装 | 本项目哪些 |
> |---|---|---|---|
> | **A. 带 dsh.bundle 的包** | package.json 里有 dsh.bundle.patch | ① profile 的 package.json 加 \名字\: \link:<路径>\ 到 dependencies<br>② 
pm install（生成 node_modules 符号链接）<br>③ profile 的 package.json 的 dsh.profile.bundles 数组加名字 | dsh-pal-channel |
> | **B. 裸文件插件** | 只有一个 .mjs 文件，没有 package.json 的 dsh 段 | profile 的 cordis.patch.yml 里写 insert + 文件绝对路径 | pc-plugin/index.mjs、pc-plugin/autopair.mjs |
>
> **判断方法**：看插件目录有没有 package.json，以及里面有没有 dsh.bundle.patch 字段。
> - 有 → 走 A（包机制，别手写 cordis.patch.yml）
> - 没有 → 走 B（cordis.patch.yml 的 insert）
>
> **搞错的后果**：A 类插件按 B 的方式写进 cordis.patch.yml 也能加载（因为能读到文件），
> 但**它的前端半边（dsh.client）不会生效** —— 表现是「有接口没界面」。
> 反过来 B 类按 A 的方式装，会因为没有 package.json 而直接失败。


这两个不是「配齐」的必要条件。**但你必须告诉用户它们的存在**，否则他不知道有这个能力
装不装由用户决定 —— **不要擅自装**，因为两者都会改变电脑端行为。

#### 插件甲：公网通道切换（`tools/pal-channel-plugin`）

**解决什么**：在 DSH 网页里一键切换公网入口（国内 frp ⇄ Cloudflare），不用每次手改 `cordis.patch.yml`。

**装它的前提**：已经配好**至少两条**公网通道。只有一条的话装了没意义（没得切）。

**怎么装**（完整步骤见 [插件 README](../tools/pal-channel-plugin/README.md)）：

**⚠️ 步骤 0（最容易漏，漏了必失败）**：先装依赖 —— 这个插件运行时需要 `yaml` 包，
它装在 `tools/remote-access/node_modules`，而 `node_modules` **不进 git**，
所以 clone 下来的目录**没有它**。实测直接加载会报 `Cannot find package 'yaml'`。

```powershell
cd <项目目录>/tools/remote-access
npm ci --ignore-scripts --no-audit --no-fund
# 成功标志：added 30 packages 左右
```

装完自检（这一步能提前发现 90% 的加载问题）：

```powershell
cd <项目目录>
node -e "import('./tools/pal-channel-plugin/lib/index.js').then(m=>console.log('LOAD OK, name=',m.name)).catch(e=>console.log('LOAD FAILED:',e.message))"
# 期望：LOAD OK, name= pal-channel
```

**步骤 1（三步包机制，**不是**手写 cordis.patch.yml）**：

> ⚠️ **2026-11-05 修正**：此前写「在 cordis.patch.yml 里 insert」是**错的**。
> 实测查证这台机器的真实机制是 DSH 的**包系统** —— 插件自带
> `package.json` 的 `dsh.bundle.patch: ./cordis.patch.yml`，DSH 会自动读它，
> **用户完全不需要手写补丁条目**（手写反而可能写错 id 或路径）。

在用户 DSH profile 目录（`%USERPROFILE%\.dsh\profiles\<desktop|web>`）做三件事：

**1a. `package.json` 的 `dependencies` 加一行**（路径用正斜杠）：

```json
"dsh-pal-channel": "link:D:/<项目目录>/tools/pal-channel-plugin"
```

**1b. 装依赖，生成 node_modules 符号链接**：

```powershell
cd <profile>
npm install --ignore-scripts --no-audit --no-fund
# 若这个 profile 是 pnpm 管的：pnpm install
```

验证符号链接建对了：

```powershell
Get-Item "<profile>\node_modules\dsh-pal-channel" | Select-Object Name,LinkType,Target
# 期望 LinkType = SymbolicLink，Target 指向 <项目目录>\tools\pal-channel-plugin
```

**1c. `package.json` 的 `dsh.profile.bundles` 数组里加 `"dsh-pal-channel"`**：

```json
{
  "dsh": {
    "profile": {
      "bundles": [ "...已有插件...", "dsh-pal-channel" ]
    }
  }
}
```

> ⚠️ **这一步最容易漏，漏了必失败**：只做 1a/1b 的话，包确实装进了
> `node_modules`，但 DSH **不会加载它** —— 因为不在 bundles 清单里。
> 表现就是「装完了，设置里什么都没有」。

**步骤 2**：重启 DSH（关掉窗口再打开）。

> **排查提示**：重启后设置里什么都没有，**第一怀疑就是步骤 0 没做**。
> 跑上面那条 `node -e` 自检就能确认。

> **对比**：另一个插件 `pc-plugin/autopair.mjs` **不需要装依赖**（只用 Node 内置模块），
> 改完配置重启即可。不要因为装了 pal-channel 就以为 autopair 也要 npm ci。

**怎么判断装成功**：DSH 设置里出现「公网通道」区块并显示当前走哪条。
命令行：`curl.exe -s "http://127.0.0.1:<端口>/api/pal-channel/status"` 返回含 `current` 的 JSON。

**安全边界（必须告知用户）**：`POST /api/pal-channel/switch` 会改 DSH 配置，
所以只允许**本机桌面**调用，配对手机一律拒绝（判据见插件 README 第四节）。

#### 插件乙：Tailscale 登录后自动配对（`pc-plugin/autopair.mjs`）

**解决什么**：手机登录 Tailscale 之后**不用再扫桌面二维码**。不装则每次换入口都要扫一次。

**装它的前提**：用户在用 Tailscale 通道。只用公网/局域网的用户装了没用。

**怎么装**（完整步骤见 [pc-plugin/README](../pc-plugin/README.md)）：

```yaml
- insert:
    - id: dsh-mobile-autopair
      name: '<项目目录>/pc-plugin/autopair.mjs'
      config:
        autopairEnabled: true
        tailscaleBin: 'C:\Program Files\Tailscale\tailscale.exe'
```

改完**必须重启 DSH**。

**怎么判断装成功**（判据明确，照抄执行；`<端口>` 换成 DSH 当前的）：

```powershell
curl.exe -s -o NUL -w "autopair=%{http_code}`n" -X POST -H "Content-Type: application/json" -d "{}" http://127.0.0.1:<端口>/dsh-mobile/autopair
curl.exe -s -o NUL -w "control =%{http_code}`n" -X POST -H "Content-Type: application/json" -d "{}" http://127.0.0.1:<端口>/dsh-mobile/nonexistent
```

- `autopair=403` 且 `control=405` → **装好了**（403 是本插件对「无转发头」的正常拒绝）
- 两个都是 405 → 没装好。查：条目写错 / DSH 没重启 / 路径不存在

**安全边界（必须告知用户）**：信任依据是「来源 IP 在 tailscaled 设备表里 + 同账号」。
但 Tailscale 1.104.2 **不提供登录名**，无法用 `tailscale-user-login` 交叉验证，
因此**同一 tailnet 同账号的设备都会被自动信任**。自用没问题；若把 tailnet 共享给别人，
应在配置里加 `allowLogins` 白名单，或在 App 的「内置通道」页关掉「登录后自动配对」。

## 四、验收必须分层，不许跳级

```
HTTP 可达      /api/pair/status 返回 200
    ↓
页面加载       日志 bridge ready + 能看到工作区
    ↓
实时通道       日志 ws OPEN + 服务端 onlineCount >= 1
    ↓
业务可用       至少一项无副作用业务响应成功
```

**上层通过不代表下层通过。构建成功 ≠ 真机通过。** 只验证到第一层就报完成 = 谎报。

`state.json` 里 `clientState` 的取值 **`running-unverified`** 只表示进程在跑，不等于手机能用。`businessVerified` 才可信，而它必须靠真机验收建立（且 run.mjs 里它硬编码为 false，别指望它自己变 true）。

> **`state.json` 在哪**：`%LOCALAPPDATA%\DSHPal\remote-access\state.json`（展开后就是你自己的用户目录下的 `AppData\Local\DSHPal\remote-access\state.json`）。**不在仓库里**，别去 `tools/remote-access/` 下找。
> **有哪些字段**：`updatedAt` / `pid` / `targetAvailable` / `targetPort` / `clientState` / `publicOrigin` / `businessVerified` / `direct[]` + 网关统计。
> **注意**：里面**没有** `running` 字段。判断网关是否活着看 `updatedAt` 是否在 30 秒内（run.mjs 每 5 秒重写一次），或直接用 `deploy-status.mjs`。

## 六·六、自启动与重启恢复（**必须主动处理，别等用户发现问题**）


### 一、先搞清楚：电脑重启后，哪些会自动恢复，哪些不会

| 组件 | 重启后自动恢复吗 | 靠什么 | 谁来装 |
|---|---|---|---|
| **DSH 本体** | ❌ **不会** | 没有自启机制，要用户手动开 | **用户本人**（装官方启动方式） |
| **网关（run.mjs）** | ✅ 会 | 计划任务 `DSH-Pal-Remote-Access`（AtLogOn 触发） | AI 用 `install-autostart.ps1` |
| **frpc 隧道客户端** | ✅ 会 | 由网关 `run.mjs` 拉起（它 spawn frpc 并带 `--watch` 自动重连） | AI（装网关时就带上了） |
| **Pal 通道插件** | ✅ 会 | DSH 启动时自动加载 `cordis.patch.yml` 里的条目 | 无需额外操作 |
| **autopair 插件** | ✅ 会 | 同上 | 无需额外操作 |
| **Tailscale Serve 配置** | ✅ 会 | Serve 配置持久化在 Tailscale 侧 | 无需额外操作 |
| **手机 App** | ✅ 会 | 手机端自己的「启动时自动连接」开关 | 用户（App 里开着） |

**结论：唯一要额外装的是「网关自启」。** 但它**必须装**，否则用户重启电脑后
手机就连不上了，而且他不会知道原因。

### 二、装网关自启（一条命令，但必须验证）

```powershell
cd <项目目录>\tools\remote-access

# 1. 先干跑，看清楚它会建什么（不会真装）
powershell -ExecutionPolicy Bypass -File .\install-autostart.ps1 -DryRun
# 期望输出：任务名 / 动作 / 工作目录 / 触发器 / 设置
# 重点看「动作」那行：必须是 wscript.exe，不能是 powershell.exe

# 2. 真装
powershell -ExecutionPolicy Bypass -File .\install-autostart.ps1
# 期望：已安装：当前用户登录时自动启动网关（零窗口）。
```

#### 为什么必须是 wscript.exe（这条不能妥协）

计划任务如果写成 `powershell.exe -WindowStyle Hidden -File xxx.ps1`，
**每次登录都会闪一个黑窗口** —— 因为 `-WindowStyle Hidden` 是「先创建窗口再隐藏」。

项目红线：后台任何控制台程序，**包括一闪而过的闪窗**，都不许出现。
唯一正确做法是 `wscript.exe` 调 `.vbs`，`.vbs` 里 `sh.Run(cmd, 0, False)`（SW_HIDE，建都不建）。

> 2026-11-05 修复：原 `install-autostart.ps1` 用的就是会闪窗的写法，已改造成
> `wscript.exe` + `run-autostart-hidden.vbs`。如果你手上的副本还是老版本，就是没更新。

#### 会装几个任务

install-autostart.ps1 会装**两个**任务（都要装，只装第一个会留下隐患）：

| 任务 | 作用 | 触发器 |
|---|---|---|
| DSH-Pal-Remote-Access | 登录时启动网关 | AtLogOn（一次性） |
| DSH-Pal-Remote-Access-Watchdog | 每 5 分钟检查，网关/frpc 掉了自动拉起 | AtLogOn + 每 5 分钟重复 |

**为什么必须有看门狗**：只有第一个任务的话，它只在**登录时**触发一次。
睡眠唤醒、注销、崩溃之后就没东西再拉起网关 —— 公网入口会一直
ERR_CONNECTION_REFUSED 直到用户下次登录，而他完全不知道发生了什么。

看门狗是**安静**的：健康时一行日志都不写；不健康才动作并记一行到
%LOCALAPPDATA%\DSHPal\remote-access\watchdog.log（超过 256 KB 自动只留尾部）。

单独跑看门狗检查状态（不动手）：

`powershell
cd <项目目录>\tools\remote-access
powershell -NoProfile -ExecutionPolicy Bypass -File .\remote-access-watchdog.ps1 -DryRun
# 健康时输出：健康：gateway pid=xxx, frpc 数量=N
`

#### 验证装对了（三步，缺一不可）

```powershell
# ① 动作必须是 wscript.exe
Get-ScheduledTask -TaskName 'DSH-Pal-Remote-Access' | ForEach-Object { $_.Actions }
# 期望 Execute = C:\WINDOWS\System32\wscript.exe
# ❌ 如果是 powershell.exe 或 cmd.exe → 装错了，会闪窗，重装

# ② 状态必须是 Ready
(Get-ScheduledTask -TaskName 'DSH-Pal-Remote-Access').State
# 期望 Ready

# ③ 实测触发一次，确认全程零窗口 + 网关真的起来
Stop-Process -Name node -ErrorAction SilentlyContinue   # 先杀掉现有网关
Start-ScheduledTask -TaskName 'DSH-Pal-Remote-Access'
Start-Sleep -Seconds 6
Get-NetTCPConnection -State Listen -LocalPort 18772 -ErrorAction SilentlyContinue
# 期望：看到 127.0.0.1:18772 在监听
```

**零窗口怎么验**：触发后**屏幕上一个窗口都不该出现**。
要严格验证可以边触发边采样（结果应为空）：

```powershell
$sw=[Diagnostics.Stopwatch]::StartNew(); $seen=@()
while($sw.ElapsedMilliseconds -lt 3000){
  $w = Get-Process cmd,powershell,conhost,wscript -ErrorAction SilentlyContinue |
       Where-Object { $_.MainWindowHandle -ne 0 }
  if($w){ $seen += $w.ProcessName }
  Start-Sleep -Milliseconds 30
}
if($seen){ "❌ 出现窗口: $($seen -join ',')" } else { "✅ 全程零窗口" }
```

> ⚠️ 第 ③ 步会短暂中断网关（约 6 秒），**用户手机上会断一下**。
> 做之前告诉用户「我要测一下重启恢复，你的手机会断几秒」。别偷偷做。

#### 失败处理

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `已存在同名任务但动作不同` | 之前用手工方式装过 | 按提示先删旧任务，或保留旧的（如果它已經是 wscript 写法） |
| 装完触发，18772 没起来 | 网关启动失败 | 看 `tools/remote-access/gateway-autostart.log` |
| 日志里 `Cannot find module` | 依赖没装 | 回「六·五 通用前置」做 `npm ci` |
| 任务 State 是 Disabled | 被禁用了 | `Enable-ScheduledTask -TaskName 'DSH-Pal-Remote-Access'` |
| 重启后仍不启动 | 触发器是 AtLogOn，用户没登录不触发 | 这是设计如此（GUI 程序需要用户会话）；告诉用户「开机后请登录一次」 |

### 三、DSH 本体要不要也设自启？（**要问用户，别自作主张**）

DSH 是 GUI 程序，设自启有两种做法，各有代价：

| 做法 | 效果 | 代价 |
|---|---|---|
| 不设（默认） | 用户自己双击打开 | 每次开机要记得开；忘了手机就连不上 |
| 放进启动文件夹 | 登录后自动打开 DSH 窗口 | 每次登录会弹出 DSH 窗口（用户可能不喜欢） |

**所以必须问**：

```
DSH 本体要不要设成开机自启？
  · 不设：每次开机你得自己双击打开 DSH，否则手机连不上
  · 设了：登录后 DSH 会自己弹出来，但你每次开机都会看到它
你要哪种？
```

**如果用户要设**：把 DSH 的快捷方式放进
`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\`
—— **不要**用计划任务 + wscript 包它（DSH 是 GUI，本来就该显示窗口）。

### 四、交付时必须告诉用户的三件事（照抄）

```
关于「重启后还能不能用」，说清三点：

1. 网关会自动启动 —— 已经装成登录自启任务，你开机登录后它自己就在跑。
2. 但 DSH 本体需要你手动打开（除非你刚才选了设自启）。
   所以流程是：开机 → 打开 DSH → 手机连上。
3. 手机 App 那边有「启动时自动连接」开关（默认开），

```

### 五、保活（连接别老断）—— 分手机端和电脑端

| 位置 | 机制 | 默认 | 怎么查/怎么调 |
|---|---|---|---|
| **手机端** | 前台服务保活（`DshLiveService`） | ✅ 开 | App 设置 → 通知与后台 →「后台保持连接」 |
| **手机端** | 电池优化（国产 ROM 会杀后台） | 需用户改 | 系统设置里把 DSH Pal 设为「不限制」。**AI 无法代做，必须用户自己点** |
| **电脑端** | 网关失败自动重试 | ✅ 内置 | `run.mjs` 自带退避重试；计划任务也配了失败重试 3 次/1 分钟 |
| **电脑端** | frpc 断线重连 | ✅ 内置 | frpc 带 `--watch`，网络抖动会自己重连 |
| **电脑端** | 网关被意外杀掉 | ✅ 有 watchdog(可选) | 仓库里有 `remote-access-watchdog` 相关脚本，但**不是默认装的**；要不要装问用户 |

> **别把「电池优化」当成 AI 能做的事**：那是系统级设置，只能用户自己在手机系统设置里点。
> 你能做的是**告诉他去哪点**（App 里有提示，或直接说「设置 → 应用 → DSH Pal → 电池 → 不限制」）。
